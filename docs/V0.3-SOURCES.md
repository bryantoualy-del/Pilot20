# V0.3 — sources de campagne

Les trois ouvrages sont **sélectionnés par défaut**. Seul le SRD 5.1 est livré.
Cocher Xanathar ou Tasha ne télécharge rien, n'installe aucune définition et ne
change pas son statut de couverture. Les PDF de référence et les packs privés
ne font jamais partie du dépôt ou de la distribution.

## Écran utilisable

Depuis la racine du dépôt : `python3 -m http.server 8000`, puis ouvrir
`http://localhost:8000/web/sources.html`.

L'écran fournit les paramètres persistants de campagne, l'import JSON privé,
les premières sélections classe/niveau/sous-classe, l'aperçu filtré des capacités
et des sorts de classe et la validation d'une requête de build complète.
Il ne remplace pas encore le futur créateur guidé complet ni le Companion.
Le catalogue de sorts affiché est la liste de classe, pas une liste de sorts
qu'un personnage de niveau donné pourrait tous lancer.

Aucun serveur applicatif, compte, téléversement ou service externe n'est requis.
Le serveur HTTP ci-dessus sert les modules locaux ; le stockage est IndexedDB.
Cette page n'est pas une application installable avec cache hors ligne : son
serveur de fichiers doit rester accessible. Le moteur et les données restent locaux.

## API

- `defaultCampaign(id)` : configuration version 1, trois sources activées,
  options facultatives désactivées. `validateCampaign` rejette versions inconnues,
  doublons et identifiants de source inconnus. Les futurs ouvrages sont hors périmètre.
- `campaignCatalog(publicPacks, privatePacks, campaign)` : validation complète
  du graphe installé, puis vue immuable filtrée par source et option. Retourne
  `index`, `installed`, `statuses`, `options` et l'instantané de configuration.
- Les consommateurs existants (`listClasses`, `listSubclasses`, `listSpells`,
  `resolveProgression`) reçoivent `context.index`. Les définitions sans
  dépendances obligatoires disponibles sont retirées ; aucun build incomplet
  n'est présenté comme valide. Les choix internes référant des entrées masquées
  sont filtrés. Les définitions installées restent intactes.
- `buildCampaignCharacter(context, request, campaign)` : garde de compatibilité,
  activation explicite du multiclassage, puis validation complète et compilation
  habituelles. Une configuration différente de celle de l'index est rejetée.
  Les options de campagne viennent de la configuration, pas du fichier personnage.
- `validateSavedPlan` : vérification préliminaire des références indisponibles ;
  **ce n'est pas** une validation de légalité. La compilation complète est obligatoire
  pour réutiliser le build après réactivation.
- `campaignRepository(storage, publicPacks)` : configuration par campagne,
  import local de packs, conservation du plan complet via `savePlan/getPlan`.
  Les records versionnés utilisent le store `meta` existant. Pas de migration
  des personnages ni des sessions épinglées, ni de suppression de choix masqués.
  Pour un build complet, le créateur doit sauvegarder son plan en plus du personnage.

## Format d'import privé

```json
{
  "kind": "pilot20-private-rule-pack",
  "schemaVersion": 1,
  "sourceId": "xge",
  "catalog": {
    "kind": "catalog",
    "schemaVersion": 3,
    "ruleset": "dnd5e-2014",
    "id": "private:my-authorized-pack",
    "items": []
  }
}
```

Le tableau vide illustre l'enveloppe ; l'import exige au moins une définition
valide. `sourceId` vaut `xge` ou `tce`. Toutes les entrées doivent déclarer une
provenance `private`. Le contrat détaillé de chaque entrée est celui de catalogue
v3. Les dépendances inter-packs doivent être installées avant le pack dépendant.
L'utilisateur confirme son autorisation d'usage local. Ce n'est pas une
certification de droits. Aucun contrôle ne peut déduire des droits du contenu JSON.

Limite : 8 Mo par pack, 100 packs et 10 000 entrées par catalogue. Versions,
références, collisions, cycles, clés de prototype, handlers arbitraires et
métadonnées d'automatisation fausses sont rejetés avant sauvegarde. L'import
est atomique avec un registre CAS contre les imports concurrents. Pas d'évaluation
de code, scripts de pack, lecture de PDF ou requête réseau par l'importeur.
La distribution publique continue de refuser les entrées privées.

Chaque capacité optionnelle utilise un `campaignOption` distinct et, si nécessaire,
`optionalClassFeature`, `requires`, `replaces`, `suppressesChoices` et
`suppressesResources`. L'activation d'un ouvrage ne choisit jamais ces options.
Une option désactivée conserve sa préférence quand son ouvrage est décoché.
Les règles globales non définies par un pack ne sont pas annoncées comme installées.

Les compteurs de couverture distinguent `automated`, `partial`, `manual`,
`unsupported`. Les statistiques portent sur des **définitions**, pas sur un
nombre de règles intégralement jouables. Les entrées manuelles/unsupported
conservent leurs limites ; une présence structurelle n'est jamais une automatisation.

## Artificier et préparation

`casting.preparation` est un champ additif optionnel : `ability-plus-level` ou
`ability-plus-half-level`. Il autorise une classe privée préparatrice sans liste
codée en dur. La politique est conservée dans le personnage v2 et réutilisée pour
compiler uniquement les sorts préparés et les sorts mineurs. Les defaults SRD
restent ceux des classes existantes. Les champs existants `startsAtClassLevel: 1`
et `multiclassRounding: ceil` couvrent les règles de slots d'une extension Artificier.
Ce contrat n'installe pas une définition complète de l'Artificier.

## Validation et limites de livraison

`tests/campaign-sources.test.js` vérifie la compilation d'un barde niveau 10 avec
une sous-classe privée **synthétique** représentant le contrat Glamour, et une
classe Artificier **synthétique** : sorts préparés, niveau 1, contribution au
multiclassage et deux capacités facultatives indépendantes. Ce sont des tests
d'intégration de mécanismes, jamais des packs officiels.

Les tests vérifient également la désactivation/réactivation sans perte de plan,
la revalidation d'un build devenu invalide, les sources mixtes, le SRD désactivé,
les imports concurrents et invalides et la persistance IndexedDB après réouverture.
La matrice privée tirée des PDF distingue l'inventaire des ouvrages, les adaptations
et le travail manuel ; elle n'est pas embarquée dans le produit.

Un test réel de l'intégralité d'un Artificier/Tasha exige encore un pack complet,
une validation métier de ses infusions, objets, listes de sorts et spécialité.
Ne pas transformer la réussite des fixtures en promesse de couverture des livres.

Contrôle d'interface effectué via DOM : état initial, absence des packs privés,
filtrage du SRD, conservation des choix, sauvegarde et réouverture. Les interactions
et IndexedDB sont vérifiés ; la revue visuelle sur iPad reste à effectuer. Le
navigateur de test n'a pas pu être installé dans cet environnement (archive de
téléchargement invalide). Ce contrôle DOM ne remplace pas une revue Safari.
