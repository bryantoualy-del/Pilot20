## Parcours Rapide

1. Nom, race/variante, classe, niveau. La galerie complète et « Créer une race » restent disponibles.
2. Sous-classe choisie par le joueur si le niveau officiel le permet ; sinon indication du niveau de déblocage.
3. Recommandations visibles puis acceptation explicite ; décisions de progression restantes ; confirmation ; sauvegarde et Companion.

Le modèle secondaire utilise la série standard selon les priorités de classe existantes, l’historique SRD disponible (Acolyte), les compétences/langues autorisées et, pour le guerrier, cotte de mailles, bouclier et épée longue. Il conserve les choix déjà renseignés. Il n’invente pas d’équipement de classe lorsqu’aucun modèle documenté n’existe. Les sorts, dons, ASI, options identitaires et sous-classes restent à choisir ; certains personnages de haut niveau demandent donc davantage de décisions sur le troisième écran. « Modifier les recommandations » ouvre les contrôles existants avec retour à Rapide.

Les statistiques d’un brouillon invalide sont provisoires. Les décisions conservées et les contenus absents restent signalés ; aucun personnage invalide ne peut être finalisé.

## Races, sources et droits

`src/catalog/data/race-discovery.json` reprend les 59 familles et 30 variantes visuelles facultatives du dossier utilisateur. C’est un inventaire de découverte, pas 59 blocs de règles installés. `raceFamilyId` et `visualAssetId` désignent l’apparence ; `rulesVersionId` et `variantId` désignent une définition mécanique. Les versions Volo et MotM d’un kobold partagent un portrait mais ne partagent jamais automatiquement leurs données.

Les portraits couvrent les 59 familles. Les 30 portraits de variantes sont facultatifs et partagent actuellement le portrait familial : leur liste et leurs noms de fichiers sont conservés dans le manifeste. Le fichier `race-variants.json` ajoute 62 entrées de métadonnées de variantes : sous-races, quatre génasi en deux éditions, drakéides de Fizban, aasimar Volo, lignées infernales, ascendants demi-elfes, férals, et les douze marques draconiques (Découverte apparaît pour deux peuples). Elles restent à définir mécaniquement dans un pack ; aucune de ces métadonnées ne vaut installation.

Vérification primaire : [Fizban](https://www.dndbeyond.com/sources/dnd/ftod), [Volo et errata](https://www.dndbeyond.com/sources/dnd/sae/volos-guide-to-monsters), [révision des gobelins/hobgobelins/kobolds MotM](https://www.dndbeyond.com/posts/1248-exploring-the-new-goblin-hobgoblin-and-kobold), et PDF utilisateur de Tasha, p. 8, pour la lignée sur mesure. L’index du PDF utilisateur de Xanathar confirme les options de classe et sorts ; aucun de ces PDF n’est embarqué.

Aucune mécanique propriétaire ni illustration officielle n’est distribuée. Les scénarios kobold et collège privé utilisent des données originales de test clairement nommées. La présence d’un PDF ne vaut pas installation d’un pack. Les neuf races SRD continuent d’utiliser leur provenance CC BY 4.0 et l’attribution existante.

## Packs privés et races maison

Un pack utilise l’enveloppe existante :

```json
{
  "kind": "pilot20-private-rule-pack",
  "schemaVersion": 1,
  "sourceId": "volo",
  "catalog": {
    "kind": "catalog",
    "schemaVersion": 3,
    "ruleset": "dnd5e-2014",
    "id": "user:example-pack",
    "items": []
  }
}
```

L’exemple décrit l’enveloppe : un vrai import exige au moins une entrée valide et des références résolues. Une entrée `race` contient `id`, `type`, `name.fr/en`, `source` et `data` validés par `validateCatalogV3`. Pour une entrée privée, `source.kind` vaut `private`. Les identifiants de sources autorisés sont centralisés dans `src/campaign/sources.js` ; la source doit aussi être activée dans la campagne. Déclarer, au besoin, dans `data` :

| Métadonnée | Sens |
|---|---|
| `raceFamilyId` / `visualAssetId` | Famille visuelle stable / asset familial |
| `variantId` / `rulesVersionId` | Sous-race ou variante / version de règles distincte |
| `sourceDocument` / `sourceVersion` / `license` | Publication, édition et droits |
| `packId` / `availability` | Provenance du pack / état informatif ; l’autorité reste l’index actif |
| `automationCoverage` / `automation` | Couverture déclarée / contrat exécutable vérifié |
| `aliases` | Recherche FR/EN |

L’éditeur maison exporte `pilot20-homebrew-race`, schéma 1, avec une `race` de provenance `homebrew/user-data`. Les noms, descriptions, apparence, taille, type, vitesses, langues, bonus, sens, maîtrises, résistances, traits et variantes restent sérialisés. La définition avancée JSON couvre les sous-races et métadonnées spécialisées. La validation refuse les valeurs hors contrat et les doublons de langues, compétences et résistances. Toute modification d’une race existante exige une nouvelle validation MJ et une nouvelle version.

Les bonus, maîtrises, résistances et vitesse au sol passent par le résolveur d’origines et le compilateur existants. Vol/escalade/nage supplémentaires, sens, type de créature, charges/repos et effets libres restent **manuels**, avec description et indications dans le Companion. Aucun nouveau moteur d’effets libres n’est introduit. Supprimer une définition réutilisable conserve les références des personnages et bloque leur revalidation tant que le contenu n’est pas réimporté.

L’assistant Tasha exige la source `tce`, l’option `tce-custom-lineage` et l’autorisation MJ. Il fixe humanoïde, Petite/Moyenne, vitesse 9 m, +2 unique, un don installé et admissible, vision dans le noir **ou** compétence, commun + une langue autorisée. Les prérequis de scores sont vérifiés sur les caractéristiques de départ avec le bonus racial ; les dépendances de don non prises en charge sont refusées. La vision et les parties manuelles du don restent déclarées manuelles. La personnalisation d’origine de Tasha demeure séparée.

## Images

Les 59 fichiers `web/assets/shared/races/<slug>.webp` sont originaux et générés pour Pilot20. Pas de référence artistique tierce copiée. Le manifeste conserve dimensions, origine, hash et variantes couvertes. Le build inclut automatiquement tous les assets dans le cache versionné. Un fichier manquant utilise `custom.svg`, également local. Le lot pèse environ 1 Mo avant compression de transport.

## Vérification et limites d’essai

Les résultats chiffrés finaux sont dans `V0.3.2-RACES-VALIDATION.md` et les preuves dans `docs/screenshots/races/`.

Les tests navigateur sont de l’émulation Chromium. Les essais physiques Safari/iPad Air 5/iPhone, clavier iOS et VoiceOver restent nécessaires. Les images sont des choix visuels originaux, pas une référence anatomique ou réglementaire officielle. Les filtres distinguent absence de pack et source désactivée ; aucune couverture mécanique n’est déduite de l’illustration.

Pour tester : `npm ci`, `npm run build:web`, `npm run dev`, ouvrir l’URL du serveur dans un navigateur. Pour iPad/iPhone sur le même réseau, lancer `npm run dev:lan` puis ouvrir `http://<adresse-IP-locale-du-poste>:4173/web/index.html` sur l’appareil. Le mode standard reste limité au poste local. Depuis l’accueil, choisir « Créer un personnage » ; Rapide est proposé par défaut. Aucun hébergement public nouveau ni fusion automatique n’a été effectué.
