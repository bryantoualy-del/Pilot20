# Persistance locale V0.2

## Contrat atomique

Les adaptateurs exposent get(store,key), list(store,prefix) et batch(conditions,writes). Une condition compare la valeur JSON attendue ; toute divergence produit StorageError(conflict). Un batch est atomique. MemoryStorage utilise copie puis commit ; IndexedDB regroupe lectures de contrôle et écritures dans une transaction readwrite native.

Une proposition de combat n'est publiée qu'après oncomplete. Quota, interruption, erreur de migration, base bloquée et conflit sont explicites. Aucun retry supprimant des données, aucun effacement de base et aucun fallback silencieux vers une sauvegarde ancienne.

## Stores

| Store | Contenu |
|---|---|
| characters | Définition permanente et indicateur archived |
| preferences | Préférences par characterId, hors calculs et historique mécanique |
| sessions | Manifeste courant, runtime, projections mécaniques épinglées, listes d'identifiants des lignes nécessaires |
| history | Une ligne par commande non-undo, snapshots runtime sans répétition des définitions |
| receipts | Une ligne par commande, résultat et empreinte V1 inchangés |
| checkpoints | Manifestes révisés à création, tous les 50 commits par défaut, ou à demande |
| archives | Lignes retirées de l'historique actif par undo ; archives complètes explicites |
| meta | Réservé aux migrations et futures métadonnées |

Les clés de combat sont sessionId/commandId. Les IDs n'acceptent pas la barre oblique. Le même personnage peut apparaître plusieurs fois grâce aux instanceId ; le même commandId peut exister dans deux sessions.

## Coût et limites

Chaque commit écrit le nouvel état courant, les nouvelles lignes d'historique/reçus et éventuellement un checkpoint. Les anciennes lignes ne sont pas réécrites. Les préférences ne sont jamais enregistrées par un combat.

Le manifeste contient encore les listes d'identifiants et les projections de participants ; sa taille grandit. Le moteur V1 reconstitue, clone et valide encore l'historique complet en mémoire. Cette livraison réduit l'amplification d'écriture et la répétition des définitions sur disque, mais **ne garantit pas une mémoire ou une latence bornées**. Les checkpoints ne remplacent pas encore une restauration ou un chargement paginé. Leur présence ne prouve pas la disponibilité d'une récupération automatique.

L'archive de session est autonome et non destructive ; sa création peut échouer par quota sans modifier la session courante. Les snapshots retirés par undo restent conservés. Les reçus sont conservés sans éviction, y compris ceux d'actions annulées : un rejeu ancien retourne son reçu ; une collision échoue.

La corruption structurelle ou une ligne absente provoque un refus lisible ; les données originales restent en place pour export/diagnostic via l'adaptateur. Aucune réparation automatique ou détection cryptographique de corruption sémantiquement valide n'est revendiquée.

## Bibliothèque

create/save exige revision 1 pour une nouvelle fiche ; la modification exige expectedRevision et nouvelle revision +1. Un conflit n'écrase pas l'autre édition. Une duplication reçoit un nouvel identifiant ; l'ID par défaut utilise crypto.randomUUID, avec générateur injectable en tests.

Une suppression exige confirmId égal au characterId. Elle supprime uniquement la fiche et ses préférences ; les combats gardent leurs projections épinglées. L'archivage masque par défaut, sans destruction. L'import refuse une collision, préserve les préférences et l'archive, mais démarre une nouvelle lignée locale à revision 1. Aucune réécriture des références de combat d'un fichier exporté n'est automatique.

## Migrations

- **Moteur V0.1** : model.migrate reste la migration historique. migrateLegacyCombat(sessionId,document,characterRefs) l'enveloppe, sur copie, sans changer reçus ni historique. Les correspondances d'identité/révision doivent être fournies explicitement ; aucune fiche permanente n'est inventée à partir des quelques statistiques de V0.1.
- **Prototype Character v1** : exactement la structure V2 sauf schemaVersion=1 et absence de revision. migrateCharacter ajoute revision=1 et passe en V2. C'est un format de test Pilot20 documenté, pas un importeur de Companion existant.
- **IndexedDB physique** : version 1 initiale avec les huit stores. Une version future inconnue est refusée ; jamais deleteDatabase. onversionchange ferme la connexion pour libérer une future migration. Les futures migrations devront copier/valider avant remplacement atomique ; aucune migration de schéma physique existante n'est inventée ici.
- **Versions futures de documents** : refusées. Un document corrompu n'est pas normalisé silencieusement. Les migrations n'altèrent pas leur entrée.

## Tests et reprise

Les suites exécutent le même contrat sur mémoire et fake-indexeddb. Une injection au deuxième put vérifie que le premier put préparé est annulé ; la dernière révision, son historique et ses reçus restent intacts. Un test de version physique future confirme que la base d'origine n'est pas supprimée. Les vrais crashes Safari et garanties de durabilité après coupure électrique nécessitent des tests navigateur ultérieurs.
