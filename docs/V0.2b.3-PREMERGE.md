# PR #7 — pre-merge safety patch

No new class, spell, combat rule, animation, transport or functional version. The existing damage policy and transaction semantics are preserved.

## Internal state versus player-facing data

`execute`, `executeCombat`, `pendingDecisions`, save/export JSON, repository records, snapshots and receipts are **trusted controller/storage APIs**. They contain supplied future dice, provisional hits, DCs, pinned definitions and continuations. They must never be forwarded verbatim to a player or an FX consumer. A local save file is not a secrecy boundary against its owner.

`src/public-view.js` provides a separate allowlisted presentation contract:

```js
const tx = execute(internalState, command, authorityContext);
// Persist tx.state internally before publishing any presentation data.
const display = transactionView(tx, {role: 'player', actorId: 'rogue'});
// Or restore a view without executing anything:
const displayState = combatView(loadedInternalState, {role: 'player', actorId: 'rogue'});
```

The host must authorize the viewer/actor binding; the projection is not authentication. Roster identities/names are assumed already approved by the host, not a new visibility/geometry model. Player views expose only their own HP/resources/economy/check identifiers and their own pending decisions. GM projection is explicit. Neither projection contains raw definitions, history, receipts, layout, source commands, future dice or continuations. Pending projections reveal no provisional hit, critical, total, future damage or save DC, even to the GM presentation surface. The internal GM controller can still inspect privileged state separately.

Completed presentation events expose only approved result fields. Players do not receive another actor's roll totals, damage/HP loss, raw typed components or DC. Final save success/failure and hit/critical status may be announced to participants; their own final totals remain available. GM final DCs are allowed. An explicit future sharing policy can broaden this conservative default. Return values are detached copies.

Internal structured events/plans remain intact for future integrations. The presentation event envelope is versioned and JSON-only: `combat.decision.requested`, `combat.resolution.completed`, `combat.transaction.undone`, with stable event/action identifiers and revision. No terminal resolution event is emitted while a choice is pending. Receipt replays emit no new event; undo is a correction, not another hit. A future FX consumer should deduplicate by identifiers and handle undo explicitly. No animations, asset bank, renderer or effect mappings are added here.

## Mixed-damage regression contract

Tests exercise one attack with repeated slashing/fire components plus cold and necrotic damage, resistance/vulnerability/immunity, reaction acceptance/refusal, temporary HP, concentration, JSON reload, receipt replay and undo. Reversing component order produces the same typed totals and final damage. Defenses are applied once per grouped type, not once per individual component and not again on a definitive result.

The existing local policy remains **group by damage type → save/interception with floor at each typed step → typed defenses → sum → temp HP → HP → concentration**. For the regression fixture, raw 36 becomes 16 after interception and 12 after defenses; temp HP absorbs 5, HP loses 7, one DC-10 concentration check results. Declining the reaction gives 27 actual damage and one DC-13 check. Raw type aggregation is independent of component insertion order.

An explicit odd mixed-type test records that 1 fire + 1 cold, each halved/floored, yields 0 under this local policy, not floor((1+1)/2). **This is not certification that every ambiguous mixed-type reduction has an official unique allocation.** A disputed allocation still uses the manual adjudication boundary. This patch does not silently change damage rules.

## Performance guardrails, not an iPad performance claim

`workloadStatus(state)` is read-only, deterministic and does not traverse historical snapshots, serialize the document, compact history or evict receipts. It reports warnings and a stop condition. `guardWorkload` runs before recursive transaction validation/cloning:

| Budget | Warning at | New-work stop at |
| --- | ---: | ---: |
| Active history entries | 250 | 1,000 |
| Durable receipts | 1,000 | 5,000 |
| Heuristic snapshot-work units | 20,000 | 100,000 |

Units = current actor weight × (history entries + 1); actor weight counts actors, declared abilities/rules and live effect/token entries. This is a conservative operational heuristic, not exact CPU/memory accounting or a device-derived latency threshold. Historical shape can differ from current shape. Existing 10 MB serialization limits remain separate.

At a stop, new work fails without mutation or spending. Export/archive and start a deliberately fresh session; never silently discard idempotence receipts. Existing receipt replays still undergo identity/collision checks. Latest undo and pending decision responses remain available, including refusal after reload, even if they momentarily exceed a limit. This bounded recovery exception prevents a guardrail itself stranding a combat. Import/read/export remain available under their existing validation/size policies; those operations can still be expensive.

CI has a 10-minute job timeout plus deterministic boundary tests; no flaky wall-clock pass/fail assertion. Full snapshot cloning/validation is not redesigned in this small patch. Safari/iPad latency, memory and long-session benchmarks remain unmeasured. Those performance risks remain a review gate before a production UI or bulk catalogue rollout.
